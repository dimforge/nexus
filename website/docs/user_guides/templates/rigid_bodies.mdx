Nexus uses Rapier's [`RigidBodyBuilder`](https://rapier.rs/docs/user_guides/rust/rigid_bodies/#creation-and-insertion)
and [`ColliderBuilder`](https://rapier.rs/docs/user_guides/rust/colliders/#creation-and-insertion) to describe the scene.
Refer to those pages for the rigid-body and collider concepts. This page explains their insertion into `NexusState`,
the settings transferred to Nexus, and the configuration of the Nexus rigid-body solver.

## Supported shapes

Start with [<rust>`ColliderBuilder::ball`, `ColliderBuilder::cuboid`, or `ColliderBuilder::capsule_y`</rust><python><rust>`ColliderBuilder::ball`</rust><python>`ColliderBuilder.ball`</python>, <rust>`ColliderBuilder::cuboid`</rust><python>`ColliderBuilder.cuboid`</python>, or <rust>`ColliderBuilder::capsule_y`</rust><python>`ColliderBuilder.capsule_y`</python></python>](https://rapier.rs/docs/user_guides/rust/colliders/#shapes).
Their dimensions and constructors are described in the Rapier guide. Nexus also supports
[<rust>`ColliderBuilder::convex_hull`</rust><python><rust>`ColliderBuilder::convex_hull`</rust><python>`ColliderBuilder.convex_hull`</python></python>](https://rapier.rs/docs/user_guides/rust/colliders/#convex-meshes),
[<rust>`ColliderBuilder::trimesh_with_flags` in 3D and `ColliderBuilder::polyline` in 2D</rust><python><rust>`ColliderBuilder::trimesh_with_flags`</rust><python>`ColliderBuilder.trimesh`</python></python>](https://rapier.rs/docs/user_guides/rust/colliders/#triangle-meshes-and-polylines).

<rust>For a 3D triangle mesh, pass [`TriMeshFlags::ORIENTED`](https://rapier.rs/docs/user_guides/rust/colliders/#triangle-meshes-and-polylines)
to `ColliderBuilder::trimesh_with_flags`. Nexus requires the resulting pseudo-normals; a mesh without them is rejected.</rust>
<python>`ColliderBuilder.trimesh` enables [`TriMeshFlags::ORIENTED`](https://rapier.rs/docs/user_guides/rust/colliders/#triangle-meshes-and-polylines)
internally.</python> Supply consistently wound triangles so their normals point outward.

:::warning
The GPU conversion doesn't implement Rapier's [heightfields](https://rapier.rs/docs/user_guides/rust/colliders/#heightfields)
or directly accept its [compound shapes](https://rapier.rs/docs/user_guides/rust/colliders/#compound-shapes).
For a non-convex dynamic object, call `state.insert_collider_in` several times as shown above. For terrain, use
<rust>`ColliderBuilder::trimesh_with_flags` in 3D or `ColliderBuilder::polyline` in 2D</rust><python><rust>`ColliderBuilder::trimesh_with_flags`</rust><python>`ColliderBuilder.trimesh`</python></python>.
:::

<rust>Here, `params.dt` is `1 / 120` seconds and `state.set_rbd_steps_per_frame(2)` selects two steps, so one call to
`pipeline.simulate` advances `1 / 60` seconds. The `params.num_solver_iterations` field controls the TGS substeps
within each rigid-body step; its default is `4`. Increasing it can improve contacts and
[joint constraints](https://rapier.rs/docs/user_guides/rust/joint_constraints/) at the expense of computations.
Calling `state.set_rbd_sim_params` marks the scene for rebuilding, so configure it before starting.</rust>
<python>Here, the timestep is `1 / 120` seconds and `state.set_rbd_steps_per_frame(2)` selects two steps, so one call to
`pipeline.simulate` advances `1 / 60` seconds. The second argument of `state.set_rbd_timestep` is the number of TGS
substeps within each rigid-body step; its default is `4`. Increasing it can improve contacts and
[joint constraints](https://rapier.rs/docs/user_guides/rust/joint_constraints/) at the expense of computations.
The default timestep is `1 / 60` seconds. `state.set_rbd_solver_params` changes the contact tolerances and solver
options through keyword arguments, and `state.rbd_solver_params()` returns their current values.</python>

<rust>`RbdSimParams` also exposes `length_unit`, `normalized_allowed_linear_error`, `normalized_prediction_distance`,
and `normalized_max_corrective_velocity`. Keep their defaults at first: setting all tolerances to zero doesn't make
contacts exact, and aggressive correction can cause jitter.</rust>
All [batch environments](./batched_simulations.mdx) must use identical `RbdSimParams` values.

After `state.finalize`, use
<rust>`state.set_rbd_gravity(backend, [0.0, -9.81, 0.0])`</rust><python>`state.set_rbd_gravity(viewer, Vec3(0.0, -9.81, 0.0))`</python>
to change gravity. The Rust setter takes a three-element array even in 2D, where its third component is ignored.
Calling `state.set_rbd_gravity` before `state.finalize` has no effect because the rigid-body buffers don't exist yet.

If a body doesn't fall, check its
[<rust>`RigidBodyBuilder::dynamic` and `ColliderBuilder::density`</rust><python><rust>`RigidBodyBuilder::dynamic`</rust><python>`RigidBodyBuilder.dynamic`</python> and <rust>`ColliderBuilder::density`</rust><python>`ColliderBuilder.density`</python></python>](https://rapier.rs/docs/user_guides/rust/rigid_bodies/#mass-properties)
configuration, then the position of `state.set_rbd_gravity` in the initialization sequence.
Use consistent units and object sizes, as discussed in
[Rapier's common mistakes](https://rapier.rs/docs/user_guides/rust/common_mistakes/).
If motion appears slow, also check how often the render loop calls `pipeline.simulate`: a fixed timestep doesn't
adapt automatically to the rendering frame rate.

## Friction model

In 3D, the friction model selects how contacts resist sliding. The default Coulomb model solves friction at each
contact point. The simplified model solves a single friction constraint at the center of each contact manifold, plus a
twist constraint resisting rotation around the contact normal. It solves fewer constraints, which helps scenes with many
resting contacts. Multibody contacts always use the Coulomb model:

## Other Rapier settings

Nexus uses its own `NexusPipeline`, and doesn't run Rapier's
[`PhysicsPipeline`](https://rapier.rs/docs/user_guides/rust/simulation_structures/).
In particular, Rapier's [sleeping](https://rapier.rs/docs/user_guides/rust/rigid_bodies/#sleeping),
[CCD](https://rapier.rs/docs/user_guides/rust/rigid_bodies/#continuous-collision-detection),
[dominance](https://rapier.rs/docs/user_guides/rust/rigid_bodies/#dominance),
[damping](https://rapier.rs/docs/user_guides/rust/rigid_bodies/#damping),
[`gravity_scale`](https://rapier.rs/docs/user_guides/rust/rigid_bodies/#gravity), and
[`RigidBody::add_force` and `RigidBody::apply_impulse`](https://rapier.rs/docs/user_guides/rust/rigid_bodies/#forces-and-impulses)
are not transferred to the ordinary GPU rigid-body solver.
The presence of a method on [`RigidBodyBuilder`](https://rapier.rs/docs/user_guides/rust/rigid_bodies/#creation-and-insertion)
is not a guarantee that Nexus implements it.

Keep the same distinction for [kinematic bodies](https://rapier.rs/docs/user_guides/rust/rigid_bodies/#rigid-body-type):
Nexus doesn't expose the per-frame [`RigidBody::set_next_kinematic_position`](https://rapier.rs/docs/user_guides/rust/rigid_bodies/#position)
workflow. Start with <rust>`RigidBodyBuilder::dynamic` and `RigidBodyBuilder::fixed`</rust><python><rust>`RigidBodyBuilder::dynamic`</rust><python>`RigidBodyBuilder.dynamic`</python>
and <rust>`RigidBodyBuilder::fixed`</rust><python>`RigidBodyBuilder.fixed`</python></python> for the scenes shown here.
